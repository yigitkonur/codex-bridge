# 03-01: Native/adversarial review schema and context proof

<objective>
Make native review and adversarial review produce one normalized, task-aware, persisted review contract. A user or later command must be able to run review against a working tree or task-bound branch and inspect structured actionable output without manually reconstructing context.
</objective>

<threat_model>
- Review target drift: review runs in the caller cwd instead of the task worktree.
- Artifact loss: review output is printed once but not saved for verdict or recovery.
- Schema split: native review and adversarial review emit incompatible shapes.
- Shell injection: review text is later passed as command-line arguments instead of JSON data.
- Generated drift: source changes are not reflected in packaged runtime bundles.
</threat_model>

<action>
Add `src/lib/review-result.mjs` exporting:

- `REVIEW_RESULT_SCHEMA_VERSION = "1.0"`;
- `normalizeNativeReviewResult(input)`;
- `normalizeAdversarialReviewResult(input)`;
- `parseNativeReviewText(text)`;
- `mapReviewVerdictToTaskVerdict(reviewResult)`;
- `validateReviewFinding(finding)`.

The normalized shape must include:

- `schema_version`;
- `review_kind` (`native` or `adversarial`);
- `verdict` (`approved`, `needs-attention`, or `must-fix`);
- `summary`;
- `findings`;
- `next_steps`;
- `target`;
- `task_id`;
- `reviewed_branch_head_sha`;
- `raw_output`.

Move reusable native review markdown parsing out of `src/adapters/codex/pipeline.mjs` or wrap it so pipeline and review command call the same implementation.
</action>
<verify>
- Add `test/review-result.test.mjs` cases for clean native output, actionable native findings, valid adversarial JSON, missing optional fields, invalid finding shapes, and verdict mapping.
- Confirm no private pipeline-only parser remains as the only review parser.
</verify>
<acceptance_criteria>
- `rg "normalizeNativeReviewResult|normalizeAdversarialReviewResult|mapReviewVerdictToTaskVerdict" src test` finds source and test use.
- Native and adversarial review produce the same top-level normalized keys.
- Invalid findings fail validation with a structured usage or type error before persistence.
</acceptance_criteria>
</task>

<task id="03-01-02" title="Bind review commands to task context">
<read_first>
- `src/codex-bridge.mjs` `executeReviewRun`
- `src/codex-bridge.mjs` `handleReviewCommand`
- `src/lib/registry.mjs` `readMeta`
- `src/lib/git.mjs` worktree metadata helpers
- `test/plugin-surfaces.test.mjs`
</read_first>
<action>
Extend review and adversarial-review parsing with value option `--task <task_id>`.

When `--task` is present:

- read the task registry `meta.json`;
- require a worktree path and branch reference in metadata;
- set review cwd to the task worktree path;
- default scope to `branch`;
- resolve the reviewed branch head SHA with `git rev-parse HEAD` in the worktree;
- include `task_id` and `reviewed_branch_head_sha` in the review request and result.

Reject conflicting target inputs clearly, for example `--task` with an explicit `--cwd` that points elsewhere.
</action>
<verify>
- Add CLI/plugin-surface tests proving `--task` appears in review/adversarial-review usage docs.
- Add deterministic tests for task metadata lookup failures: missing task, missing worktree path, missing branch/head.
</verify>
<acceptance_criteria>
- `review --task <task_id> --json` and `adversarial-review --task <task_id> --json` route through the task worktree context.
- Missing or malformed task metadata produces a structured validation error, not a review against the wrong cwd.
- Review JSON output includes `result.review_result.task_id` and `result.review_result.reviewed_branch_head_sha` when task-bound.
</acceptance_criteria>
</task>
