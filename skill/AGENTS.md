# skill/AGENTS.md

The Claude Code skill bundle. Part authored, part generated by `npm run build`. Know which is which before editing.

Root rules live in `/AGENTS.md`. This file covers the skill-specific conventions: what is authored vs. generated, how `SKILL.md` and `config.yaml` work, what the references are for, and rules for adding skill-only docs.

## Authored vs generated

| Path | Source of truth | In git? |
|---|---|---|
| `skill/SKILL.md` | **Hand-edited.** User-facing skill doc. | Yes |
| `skill/config.yaml` | **Hand-edited.** Default config shipped with the skill. | Yes |
| `skill/references/**.md` | **Hand-edited.** Reference docs. | Yes |
| `skill/references/templates/*.md` | **Hand-edited.** Example mission templates. | Yes |
| `skill/scripts/codex-bridge.mjs` | **Committed build output.** Generated from `src/codex-bridge.mjs` via esbuild. | Yes |
| `skill/app-server-broker.mjs` | **Committed build output.** Generated from `src/app-server-broker.mjs` via esbuild. | Yes |
| `skill/prompts/*.md` | **Committed build output.** Copied from `src/prompts/` by esbuild. | Yes |
| `skill/schemas/*.json` | **Committed build output.** Copied from `src/schemas/` by esbuild. | Yes |
| `skill/templates/*.md` | **Committed build output.** Copied from `src/templates/` by esbuild. | Yes |

The build outputs are committed so that `npx skills add yigitkonur/codex-bridge` works without a build step on the user's machine. CI verifies the committed bundle matches a fresh `npm run build` — see `.github/workflows/build.yml`. After any change under `src/`, run `npm run build` and commit the resulting diff alongside your source changes.

## `SKILL.md`

Claude Code parses front matter to register the skill:

```yaml
---
name: codex-bridge
description: >
  Orchestrate Codex as Claude Code's execution aide. Use when delegating 
  coding tasks, reviews, or multi-step work to Codex. Manages plan→execute→review 
  cycles with Monitor-based notifications.
compatibility: Requires Node.js 22+ and codex CLI (npm i -g @openai/codex)
allowed-tools: Bash(node *) Monitor
---
```

The body is consumed by Claude when the skill is active. It teaches: quick-start, lifecycle (plan → approve → execute → auto-pipeline → final notification), how to respond to each event tag, standalone review, advanced features (steer, summary, heartbeat), config pointers.

Rules for editing `SKILL.md`:

- Keep `allowed-tools` minimal. `Bash(node *)` + `Monitor` is what the skill needs; adding more broadens what Claude can do and weakens the skill's safety posture.
- Keep the quick-start runnable. Every command in the first section must work verbatim against a current build of `skill/scripts/codex-bridge.mjs`.
- When code in `src/` changes a command name, flag, or event tag, `SKILL.md` is the first place to update, then the references, then the Gherkin specs.

## `config.yaml`

The full schema lives in `src/lib/config.mjs::DEFAULT_CONFIG`. `config.yaml` is a commented copy for end-users.

Top-level key is `codex_bridge:`. Keys (all optional — defaults in `DEFAULT_CONFIG`):

- `mode`: `plan | default`. Default `plan`. Plan forces `effort: xhigh` regardless of the `effort` setting.
- `model`: upstream model name (default `gpt-5.4`).
- `effort`: `none | minimal | low | medium | high | xhigh`. Default `xhigh`.
- `auto_review`: run adversarial-style review after execution. Default `true`.
- `post_task_prompt`: prompt for the completion check stage. Empty string disables.
- `allow_questions`: allow `requestUserInput` during execution. Default `true`. Plan mode always allows.
- `session_dir`: where session files are written. Default `~/.codex-bridge/sessions`.
- `sandbox_policy`: `danger-full-access | workspace-write | read-only`. Default `danger-full-access` (shipped since v1.2.0 — lets Codex commit its own work).
- `skip_meta_skills`: prepend an orchestrator directive telling Codex to skip internal planning/ceremony skills. Default `true`.
- `command_failure_circuit_breaker`: emit `[WARNING]` after N same-family command failures (sliding window of 5). Default `true`.
- `idle_timeout_ms`: max gap between notifications before a turn is failed with `ClientTimeout`. Default `300_000` (5 min).
- `turn_plan_ms` / `turn_default_ms`: per-turn wall-clock ceiling. Default `1_800_000` each (30 min).
- `pipeline_stage_ms` / `pipeline_total_ms`: per-stage and total auto-pipeline budgets. Defaults `300_000` / `900_000` (5 min / 15 min).
- `question_answer_ms`: how long `requestUserInput` waits for an answer. Default `300_000`.
- `prompt_footer`: text appended to every user prompt. Default instructs Codex to use the `requestUserInput` tool for questions.

When adding a new config key:

1. Add to `DEFAULT_CONFIG` in `src/lib/config.mjs`.
2. Add a commented-out example in `skill/config.yaml`.
3. Document in `skill/references/config-reference.md`.
4. Add a scenario in `gherkin-tests-v2/03-config/`.

## References directory

`skill/references/*.md` are hand-authored end-user docs. Keep each short and scoped to a single surface area.

| File | Scope |
|---|---|
| `command-reference.md` | Every CLI subcommand, its flags, and its exit codes. |
| `config-reference.md` | Every `config.yaml` key, default, and interplay. |
| `monitor-patterns.md` | Presets and bash snippets for `Monitor` tool setup. |
| `notification-format.md` | Exact wire format of `[PLAN]`, `[QUESTION]`, `[CONFIRMED]`, `[PIPELINE:*]`, `[DONE]`, `[INCOMPLETE]`, `[ERROR]`, `[REVIEW]`. Must track `src/lib/session-log.mjs`. |
| `ndjson-guide.md` | Fields in `{threadId}.ndjson` and how to query with `jq`. |
| `orchestration-flows.md` | End-to-end flow diagrams for simple task, question path, review findings, incomplete result. |
| `prompt-writing.md` | Tips for writing effective prompts to hand to Codex. |
| `error-recovery.md` | Error type → cause → recovery mapping. Must track `codexErrorInfo` variants in `src/lib/codex.mjs`. |
| `templates/coder-mission.md` | Example prompt for coder tasks. |
| `templates/research-mission.md` | Example prompt for research tasks. |
| `templates/test-runner.md` | Example prompt for test-automation tasks. |

Cross-links within references should use relative paths (`[notification format](notification-format.md)`) — they resolve both in GitHub and in the shipped skill bundle.

## Build contract

`npm run build` (at repo root):

1. esbuild bundles `src/codex-bridge.mjs` → `skill/scripts/codex-bridge.mjs`. No shebang (invoked via `node <file>`, not as an executable).
2. `esbuild.config.mjs` `copies` array copies:
   - `src/prompts/adversarial-review.md` → `skill/prompts/adversarial-review.md`
   - `src/schemas/review-output.schema.json` → `skill/schemas/review-output.schema.json`
   - `src/templates/execute-instructions.md` → `skill/templates/execute-instructions.md`
   - `src/templates/plan-enforcement.md` → `skill/templates/plan-enforcement.md`

If `src/` grows a new prompt, schema, or template, **add it to `copies`**. The runtime path resolution in `src/codex-bridge.mjs::ROOT_DIR` handles both `src/` and `skill/scripts/` layouts automatically.

## Rules for contributors

1. **Never hand-edit generated files under `skill/`.** The next build overwrites them. Edit `src/` and run `npm run build`.
2. **Commit the build diff alongside the source diff.** The bundle under `skill/scripts/`, `skill/app-server-broker.mjs`, `skill/prompts/`, `skill/schemas/`, `skill/templates/` ships to users as-is via `npx skills add` — it must be up to date on every main-branch commit. CI fails the build on drift.
3. **Front matter in `SKILL.md` is load-bearing** — Claude Code parses it. Wrong YAML or missing keys break skill discovery.
4. **Keep reference files diffable.** No mechanically-generated content; no TOCs that need re-generation.
5. **Keep examples runnable.** Every command in a reference should work against the checked-in `skill/scripts/codex-bridge.mjs`.
